# GhostType

OSS Windows-first Cotypist clone (https://cotypist.app/). System-wide inline autocomplete: ghost text at caret in any app, Tab accepts. Rust.

## Build
- Toolchain pinned `rust-toolchain.toml`; bump with `rust-version`.
- `cargo run` = app (default member `crates/ghosttype`, bin `GhostType`).
- Pre-commit = CI, all must pass: `cargo fmt --all --check`; `cargo clippy --workspace --all-targets` (`RUSTFLAGS=-D warnings`); `cargo test --workspace`; `cargo doc --workspace --no-deps`.
- GPU backends (Windows, opt-in): `cargo run --features vulkan,cuda`. The default build runs models on the CPU only. `vulkan` needs the Vulkan SDK (`VULKAN_SDK`). `cuda` needs the CUDA Toolkit and the CUDA DLLs on `PATH` at run time. Local build settings go in `.cargo/config.local.toml` (gitignored, loaded by `.cargo/config.toml`). Copy `.cargo/config.local.example.toml` to start. It sets the Ninja generator (the Visual Studio generator finds no CUDA toolset), `CUDACXX`, a short target folder (the Vulkan shader build goes past `MAX_PATH`), and `CMAKE_CUDA_ARCHITECTURES` for the local GPU only (much faster CUDA build). CMake configures llama.cpp only one time: after a change in `[env]` or a failed CMake step, run `cargo clean -p llama-cpp-sys-2`.
- Windows settings window: WinUI 3 through `windows-reactor`, a git dependency on windows-rs `master` at a fixed commit (the release 0.100.0 has no `AppProxy` and no public `App::run_with`). It is framework-dependent: running GhostType needs the Windows App Runtime 2 installed. A self-contained build (`windows-reactor-setup` in `build.rs`) adds about 30 MB.
- Prompt eval: `cargo run --release -p ghosttype_llm --example prompt_eval -- MODEL.gguf crates/ghosttype_llm/examples/prompt_eval/cases/tuning.jsonl --baseline crates/ghosttype_llm/examples/prompt_eval/baselines/<model>.tuning.jsonl`. It prints the word scores, the median time, the cases that a change helped or harmed, and the mean log probability of the next word with its change. The log probability moves for small changes that leave the word scores the same. `--notes TEXT` sets the notes about the writer. `--backend cpu|vulkan|cuda|metal` sets the backend (default: Metal on macOS, else the CPU). A change to the prompt or to the context must show a gain here before it ships.
- Settings file: `%LOCALAPPDATA%\GhostType\settings.json` on Windows, `~/Library/Application Support/GhostType/settings.json` on macOS (the General and Screen text panes write it).
- Windows autostart: the General pane writes the `GhostType` value in `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. It starts the program that wrote it. To turn it on also removes the `GhostType` value in `...\Explorer\StartupApproved\Run`, so a stop from Task Manager does not stay.
- macOS autostart: the General pane writes the launchd agent `~/Library/LaunchAgents/io.github.israperez98.ghosttype.plist`. It starts the program that wrote it.

## Layout
Virtual workspace, flat `crates/`.
- `ghosttype_core`: engine, matching, accept state machine, prompt (a fixed frame that the user cannot edit, the notes about the writer from the General pane, place line, text around the caret, clipboard, screen text, a budget of estimated tokens for each section), the format of known apps and web pages (`place`), the screen text that the prompt keeps (`screen`: noise, distance to the caret, budget), settings model, Models, Playground, General and Screen text panes. The CPU backend always uses short suggestions, and the General pane shows the length without a choice. A screen read starts at the first key of a session and when the input settles, unless the session has its final screen text. A session first uses the stored screen text. The answer of its own read replaces that text one time, when the text changed. When the read of the accessibility tree gives no lines and the platform can do an OCR, core asks for an OCR read. The level of the Screen text pane (fast or accurate) shows only when the OCR of the platform has levels (`OcrLevels`). The `Controller` runs GhostType from the platform events (keys, clicks, timers, tray, settings window, service answers). Pure Rust, no OS. Each platform implements the `Shell` trait: it reads the desktop (`Desktop`) and does the OS effects that the controller asks for. The platform runtimes only translate OS events into controller calls. Each pane gives its page of the settings window as a tree of sections and rows (`settings_view`), with a stable id for each control. Each platform has one renderer for each kind of row and sends back what the user did with a control, so a new setting needs no platform code.
- `ghosttype_windows`: hooks, overlay, badge at the caret, `SendInput`, tray (Win32, main thread). Caret reader on its own thread: the system caret, else UI Automation (UIA) for apps that draw their own caret (browsers, Electron, WinUI). It also reads the text around the caret (UIA `TextPattern`, else a classic edit control) and the field label (UIA `Name`, else `HelpText`) 40 ms after each key, click and focus move. The shell keeps that read for the hook, because the hook must not wait for UIA. Screen text reader on its own thread with a low priority: the UIA text elements of the foreground window, else the OCR of a band of the window around the field (`Windows.Graphics.Capture` and `Windows.Media.Ocr`). The OCR needs Windows 11, because Windows 10 draws a border around the window at each capture. It stops while energy saver is on. Settings window (WinUI 3 through windows-reactor, on its own UI thread). The physical cores of the CPU and their efficiency classes (`cpu_cores`). All FFI.
- `ghosttype_macos`: event tap, Accessibility (AX) for the caret, the text around it, the field label and the host of the web page, the static text of the focused window, else the OCR of a band of the window around the field (`ScreenCaptureKit` and Vision, only with the Screen & System Audio Recording permission). The screen reads run one at a time on a dispatch queue with a low priority. Overlay panel, CGEvent injection, menu bar extra, settings window. All FFI. Needs Accessibility access (`cargo run` from a terminal: grant it to the terminal app). The OCR also needs Screen & System Audio Recording, which `cargo run` also takes from the terminal app.
- `ghosttype_models`: Hugging Face search, downloads and the local models directory (`ModelHub`). HTTPS + file IO, no FFI.
- `ghosttype_llm`: runs GGUF models with llama.cpp (`llama-cpp-2`) on one worker thread (`ModelRunner`), on the backend that each load names (CPU, Vulkan, CUDA, Metal). macOS always loads on Metal. On the CPU, a prompt runs one thread on each performance core of the `CpuCores` that the bin gives (at least 4 threads when the CPU has 4 cores), and each added token runs on at most 4 threads. Without `CpuCores` (macOS, tests, eval), and on the GPU backends, llama.cpp keeps its threads. Refuses a GPU load when the whole model does not fit in free GPU memory. Heals the last word of each prompt (token healing). Keeps the last prompt in the llama.cpp cache, so the next prompt decodes only the tokens that it adds. For a recurrent model (Qwen3.5), it also saves the state before each of the last words, so a backspace across a word does not decode the full prompt again. Sends the text of a completion while it grows. A drop of `LlamaCpp` waits until the worker frees the model, because on Metal llama.cpp stops the process with an assert when the process exits with a loaded model (macOS quits through `exit`). With the "Show words early" setting, the engine shows its complete words at once. Build needs CMake and libclang.
- `ghosttype`: bin. Wiring, config, logging, event loop.

## Rules
`.claude/rules/` (binding; path-scoped ones load with matching files):
- `tdd.md` test-first workflow · `clean-code.md` naming, structure, no comments · `architecture.md` crate boundaries, traits
- `portability.md` logic in core; platform crates only translate, so OS ports never touch core
- `rust.md` API, errors, docs, types · `dependencies.md` Cargo · `windows.md` FFI, threads, runtime invariants · `windows-ui.md` Windows 11 look & feel (Fluent) · `macos-ui.md` macOS look & feel (Apple HIG, Liquid Glass) · `git.md` · `ste100.md` Simplified Technical English for prose and UI strings
