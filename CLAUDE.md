# GhostType

OSS Windows-first Cotypist clone (https://cotypist.app/). System-wide inline autocomplete: ghost text at caret in any app, Tab accepts. Rust.

## Build
- Toolchain pinned `rust-toolchain.toml`; bump with `rust-version`.
- `cargo run` = app (default member `crates/ghosttype`, bin `GhostType`).
- Pre-commit = CI, all must pass: `cargo fmt --all --check`; `cargo clippy --workspace --all-targets` (`RUSTFLAGS=-D warnings`); `cargo test --workspace`; `cargo doc --workspace --no-deps`.
- GPU backends (Windows, opt-in): `cargo run --features vulkan,cuda`. The default build runs models on the CPU only. `vulkan` needs the Vulkan SDK (`VULKAN_SDK`). `cuda` needs the CUDA Toolkit and the CUDA DLLs on `PATH` at run time. Local build settings go in `.cargo/config.local.toml` (gitignored, loaded by `.cargo/config.toml`). Copy `.cargo/config.local.example.toml` to start. It sets the Ninja generator (the Visual Studio generator finds no CUDA toolset), `CUDACXX`, a short target folder (the Vulkan shader build goes past `MAX_PATH`), and `CMAKE_CUDA_ARCHITECTURES` for the local GPU only (much faster CUDA build). CMake configures llama.cpp only one time: after a change in `[env]` or a failed CMake step, run `cargo clean -p llama-cpp-sys-2`.
- Windows settings window: WinUI 3 through `windows-reactor`, a git dependency on windows-rs `master` at a fixed commit (the release 0.100.0 has no `AppProxy` and no public `App::run_with`). It is framework-dependent: running GhostType needs the Windows App Runtime 2 installed. A self-contained build (`windows-reactor-setup` in `build.rs`) adds about 30 MB.
- Prompt eval: `cargo run --release -p ghosttype_llm --example prompt_eval -- MODEL.gguf crates/ghosttype_llm/examples/prompt_eval/cases/tuning.jsonl --baseline crates/ghosttype_llm/examples/prompt_eval/baselines/<model>.tuning.jsonl`. It prints the word scores, the median time and the cases that a change helped or harmed. A change to the prompt or to the context must show a gain here before it ships.
- Settings file: `%LOCALAPPDATA%\GhostType\settings.json` on Windows, `~/Library/Application Support/GhostType/settings.json` on macOS (the General pane writes it).
- Windows autostart: the General pane writes the `GhostType` value in `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. It starts the program that wrote it. To turn it on also removes the `GhostType` value in `...\Explorer\StartupApproved\Run`, so a stop from Task Manager does not stay.
- macOS autostart: the General pane writes the launchd agent `~/Library/LaunchAgents/io.github.israperez98.ghosttype.plist`. It starts the program that wrote it.

## Layout
Virtual workspace, flat `crates/`.
- `ghosttype_core`: engine, matching, accept state machine, prompt (system prompt, place line, text around the caret, clipboard), the format of known apps and web pages (`place`), settings model, Models, Playground and General panes. The `Controller` runs GhostType from the platform events (keys, clicks, timers, tray, settings window, service answers). Pure Rust, no OS. Each platform implements the `Shell` trait: it reads the desktop (`Desktop`) and does the OS effects that the controller asks for. The platform runtimes only translate OS events into controller calls. Each pane gives its page of the settings window as a tree of sections and rows (`settings_view`), with a stable id for each control. Each platform has one renderer for each kind of row and sends back what the user did with a control, so a new setting needs no platform code.
- `ghosttype_windows`: hooks, overlay, badge at the caret, `SendInput`, tray (Win32, main thread). Caret reader on its own thread: the system caret, else UI Automation (UIA) for apps that draw their own caret (browsers, Electron, WinUI). It also reads the text around the caret (UIA `TextPattern`, else a classic edit control) and the field label (UIA `Name`, else `HelpText`) 40 ms after each key, click and focus move. The shell keeps that read for the hook, because the hook must not wait for UIA. Settings window (WinUI 3 through windows-reactor, on its own UI thread). All FFI.
- `ghosttype_macos`: event tap, Accessibility (AX) for the caret, the text around it, the field label and the host of the web page, overlay panel, CGEvent injection, menu bar extra, settings window. All FFI. Needs Accessibility access (`cargo run` from a terminal: grant it to the terminal app).
- `ghosttype_models`: Hugging Face search, downloads and the local models directory (`ModelHub`). HTTPS + file IO, no FFI.
- `ghosttype_llm`: runs GGUF models with llama.cpp (`llama-cpp-2`) on one worker thread (`ModelRunner`), on the backend that each load names (CPU, Vulkan, CUDA). Metal on Apple silicon. Refuses a GPU load when the whole model does not fit in free GPU memory. Heals the last word of each prompt (token healing). Keeps the last prompt in the llama.cpp cache, so the next prompt decodes only the tokens that it adds. For a recurrent model (Qwen3.5), it also saves the state before each of the last words, so a backspace across a word does not decode the full prompt again. Sends the text of a completion while it grows. A drop of `LlamaCpp` waits until the worker frees the model, because on Metal llama.cpp stops the process with an assert when the process exits with a loaded model (macOS quits through `exit`). With the "Show words early" setting, the engine shows its complete words at once. Build needs CMake and libclang.
- `ghosttype`: bin. Wiring, config, logging, event loop.

## Rules
`.claude/rules/` (binding; path-scoped ones load with matching files):
- `tdd.md` test-first workflow · `clean-code.md` naming, structure, no comments · `architecture.md` crate boundaries, traits
- `portability.md` logic in core; platform crates only translate, so OS ports never touch core
- `rust.md` API, errors, docs, types · `dependencies.md` Cargo · `windows.md` FFI, threads, runtime invariants · `windows-ui.md` Windows 11 look & feel (Fluent) · `macos-ui.md` macOS look & feel (Apple HIG, Liquid Glass) · `git.md` · `ste100.md` Simplified Technical English for prose and UI strings
