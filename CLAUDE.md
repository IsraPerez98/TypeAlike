# GhostType

OSS Windows-first Cotypist clone (https://cotypist.app/). System-wide inline autocomplete: ghost text at caret in any app, Tab accepts. Rust.

## Build
- Toolchain pinned `rust-toolchain.toml`; bump with `rust-version`.
- `cargo run` = app (default member `crates/ghosttype`, bin `GhostType`).
- Pre-commit = CI, all must pass: `cargo fmt --all --check`; `cargo clippy --workspace --all-targets` (`RUSTFLAGS=-D warnings`); `cargo test --workspace`; `cargo doc --workspace --no-deps`.
- GPU backends (Windows, opt-in): `cargo run --features vulkan,cuda`. The default build runs models on the CPU only. `vulkan` needs the Vulkan SDK (`VULKAN_SDK`). `cuda` needs the CUDA Toolkit and the CUDA DLLs on `PATH` at run time. Local build settings go in `.cargo/config.local.toml` (gitignored, loaded by `.cargo/config.toml`). Copy `.cargo/config.local.example.toml` to start. It sets the Ninja generator (the Visual Studio generator finds no CUDA toolset), `CUDACXX`, a short target folder (the Vulkan shader build goes past `MAX_PATH`), and `CMAKE_CUDA_ARCHITECTURES` for the local GPU only (much faster CUDA build). CMake configures llama.cpp only one time: after a change in `[env]` or a failed CMake step, run `cargo clean -p llama-cpp-sys-2`.
- Windows settings window: WinUI 3 through `windows-reactor`, a git dependency on windows-rs `master` at a fixed commit (the release 0.100.0 has no `AppProxy` and no public `App::run_with`). It is framework-dependent: running GhostType needs the Windows App Runtime 2 installed. The `self-contained` feature (`windows-reactor-setup` in `build.rs`) copies the runtime next to the program instead. It adds about 30 MB, and the Windows installers use it.
- Release: push a tag `vX.Y.Z` equal to the workspace version. `.github/workflows/release.yml` builds `GhostType-X.Y.Z-macos-arm64.dmg` (ad-hoc signature, no notarization) and two Windows installers, then makes a draft release. `-windows-x64-vulkan-setup.exe` has Vulkan. `-windows-x64-cuda-setup.exe` has Vulkan and CUDA with the cuBLAS DLLs. A manual run (`workflow_dispatch`) builds only the workflow artifacts. The scripts are in `packaging/`: `macos/build-dmg.sh` (app bundle from `Info.plist`, disk image), `windows/stage.ps1` (the files from the release folder, the Visual C++ runtime, cuBLAS) and `windows/GhostType.iss` (Inno Setup, current user only, `%LOCALAPPDATA%\Programs\GhostType`). `release.yml` pins MSVC 14.44, CUDA and the Vulkan SDK.
- Prompt eval: `cargo run --release -p ghosttype_llm --example prompt_eval -- MODEL.gguf crates/ghosttype_llm/examples/prompt_eval/cases/tuning.jsonl --baseline crates/ghosttype_llm/examples/prompt_eval/baselines/<model>.tuning.jsonl`. It prints the word scores, the median time, the cases that a change helped or harmed, and the mean log probability of the next word with its change. The log probability moves for small changes that leave the word scores the same. The median time is the time on the first key, when the model did not decode the prompt before. The warm time is the time after the model decoded the prompt when the input settled. It also prints the median tokens of a prompt and the time for each token. `--notes TEXT` sets the notes about the writer, and `--name TEXT` the name of the writer. `--backend cpu|vulkan|cuda|metal` sets the backend (default: Metal on macOS, else the CPU). `--cpu-cores 4,6` gives the performance and efficiency cores, so that the CPU backend uses the threads of the app on Windows. `--word-choice off|light|medium|strong` sets the word bias (default: off). `--word-bias off` turns off only the word bias, and keeps the next-word bias and the phrases. `--shared-history on|off` gives each app of a case the scope "All apps" (default) or "Only this app". It also prints the right and the wrong words that show, a table for a minimum probability of the first word, and a table for each cut of the tail. `--tail-cut off` turns off the cut of the app: use it to choose a cut. `--length very_short|short|medium|long|very_long` sets the suggestion length, with its token limit and its cut (default: medium). The CPU backend allows at most short, so measure a longer length on a GPU backend. `--typo-rule on|off` sets the rule for typos (default: on, as in the app). The report then gives a table for each cut of the typed letters: the typo cases that it catches and the other cases that it hides. Run it with `--typo-rule off` to choose a cut. `cases/chat.jsonl` has one or two characters in chats, emails and documents. Run it also with `--notes`. `cases/new_line.jsonl` has cases that end with Enter (a case with a line break at the end of `before`, or with `before_enter`). Run it with `--name "Sara Novak"`. `cases/mid_line.jsonl` has cases with text after the caret on its line. There `next` is all the text up to that text, and each word of a suggestion after `next` is wrong. Run it for a change to the text after the caret or to the filters of a suggestion. On `cases/typos.jsonl`, a case matches when no suggestion finishes the word with the typo. Each typo case has `fixed`, the text before the caret without the typo, and the report counts the fixes that write the meant word (`typo fixes`) and the fixes of words without a typo (`other fixes`). A change to the prompt or to the context must show a gain here before it ships. `cases/left_out.jsonl` has cases from the stores of the writers, each with one text of its store left out of the history (`left_out`). Run it with each `--word-choice` for a change to the word bias, and compare it with the run with `--word-choice off`. The `shared` group of the stores files has cases where the next word comes from another app (`help`), where another app pushes a wrong word (`harm`), and where the place and another app give different next words (`priority`). Run them with `--word-choice medium` for a change to the scope of the history.
- Settings file: `%LOCALAPPDATA%\GhostType\settings.json` on Windows, `~/Library/Application Support/GhostType/settings.json` on macOS (the General, Screen text and Personalization panes write it through `ghosttype_settings::SettingsFile`).
- Log file: `GhostType.log` in the temp folder (`%TEMP%` on Windows, `$TMPDIR` on macOS), next to the terminal output. Each start adds to it, so the log of a crash stays. A start moves a log above 10 MB to `GhostType.previous.log`. `GHOSTTYPE_LOG` sets the levels in the syntax of `tracing_subscriber::filter::Targets` (default `info`), for example `debug` or `info,ghosttype_llm=debug`. The llama.cpp logs have the target `llama-cpp-2`. A panic also goes to the log. The first line of each start gives the version and the GPU features of the build. `docs/logging.md` tells how to read the log and gives the rules for new log lines.- Earlier writing: `history.bin` in the folder of `settings.json`, only while "Use earlier writing" is on. It is sealed with ChaCha20-Poly1305. The key is a generic password in the login keychain on macOS (service `io.github.israperez98.ghosttype`, account `history-key`), and `history.key` (locked with DPAPI) next to `history.bin` on Windows. To delete both resets the history.
- Windows autostart: the General pane writes the `GhostType` value in `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. It starts the program that wrote it. To turn it on also removes the `GhostType` value in `...\Explorer\StartupApproved\Run`, so a stop from Task Manager does not stay (`ghosttype_windows::StartupEntry`).
- macOS autostart: the General pane writes the launchd agent `~/Library/LaunchAgents/io.github.israperez98.ghosttype.plist` (`ghosttype_macos::LaunchAgent`). It starts the program that wrote it.

## Layout
Virtual workspace, flat `crates/`. A module with children is `foo.rs` plus `foo/` (never `mod.rs`, clippy `mod_module_files`). A large module is a facade: its children are private and it re-exports their items with explicit `pub use`, so each item keeps one path. `settings_window` is different: it only groups the public pane modules and `view`. A large unit test suite is in `foo/tests.rs` (groups in `foo/tests/`). The tests of several core modules share `test_support.rs`. `history` and the llm `worker` have their own `test_support.rs`.
- `ghosttype_core`: engine, matching, accept state machine, prompt (in the first person: a fixed frame that the user cannot edit, the notes about the writer from the General pane (a default text in the first person when the settings file has no notes), the name of the writer, place line, text around the caret, clipboard, screen text, a budget of estimated tokens for each section, and a heading just before the text before the caret), the format of known apps and web pages (`place`), the screen text that the prompt keeps (`screen`: noise, the times of chat headers, distance to the caret, budget, the lines above and below the caret. The lines below come first, then the lines above. The text after the caret comes last, next to the heading, so that the model writes text that leads into it), the earlier writing of the user (`history`: the texts of finished sessions without their secrets and without the text that the user did not write. The place of a text is its web page in any browser, else its app. Each app of the Personalization pane has a scope: Off, Only this app or All apps. A session uses only the texts of its pool: the texts of its own app with "Only this app", else the texts of all the apps with "All apps". A text never replaces or continues a text of another pool. When the store has more than 2000 texts, the oldest text of the place with the most texts goes. The examples of the prompt (the texts of the same place that match the topic of the field: one on the CPU, two on a GPU. In a place with at most 3 texts, its newest texts fill up to two examples. The texts of other places of the pool that share at least 3 topic words with the field fill the free examples. A place without texts gets the newest text of another place with the same format), the word bias of each pool with its spelling, the phrases that the writer repeats (when the word choice is on, a word that came after the same 3 words at least 3 times, and in at least 60 percent of the times, shows without the model while the line after the caret is empty), the next-word bias (at most 8 words that came after the last 3 words before the caret, else the last 2, each with the strength times its share. The runs that came only one time are left out). The phrases and the next words come from the texts of the place when these texts have the last words, else from all the texts of the pool. The core also has the `WritingHistory` and `KeyVault` traits), settings model, Models, Playground, General, Screen text and Personalization panes. The suggestion lengths go from very short (3 tokens) to very long (22 tokens), with medium (10 tokens) as the default. Each length also gives the cut of the tail of its requests: about 2 percent up to medium, and a lower cut for long and very long, so that each token can be as unsure as at medium. On the CPU backend, the General pane offers only very short and short, and a longer saved length works as short. The badge at the caret opens a menu (`BadgeMenu`): pause or resume, the screen text switch of the app where the user types, and the scope of its earlier writing (Off, Only this app, All apps). An entry is dimmed while the main switch of its pane is off, and a pick changes the settings as the pane does. The rule for typos (the General pane, on by default) gives each request a minimum for the typed letters of the last word (`TypoRule::typed_letters_cut`, sent as `TypoCheck`). With "Fix typos" (on by default, shown while the rule is on), the request also asks for a fix. A completion with a `Correction` shows the typed letters struck through and the fixed word after the caret (`Reaction::ShowFix`, `Ghost::Fix`), and Tab deletes the typed letters and types the fixed word (`Reaction::Replace`). Tab types the next part of a suggestion: the next word with the whitespace before it. The closing punctuation, quotes and brackets at the end of a word (`CLOSING_SIGNS`) are not a part of that word. They go into the part of the next word that is not only signs, without the signs at the end of that word, also after a fix ("Best| regards, Sam" takes " regards", then ", Sam"). Signs at the end of a suggestion are a part of their own. Tab takes a suggestion only while the ghost text shows on the screen (`Desktop::is_ghost_shown`). After a Tab, the rest of the suggestion also counts as shown while it waits for the caret, so that a quick Tab types its next part. After the last part, core asks for the next suggestion as after a typed key (`AfterAccept::Next`). When the completion still runs, core asks when that completion ends without more text. Until the next suggestion shows, a quick Tab does not reach the app while a suggestion can still come (`TabHold`, at most 800 ms): after a request, a shown phrase or a completion that still runs (`App::has_offer`). Core swallows that Tab and keeps the session. The held Tab does not take the next suggestion, because Tab types only text that the user saw. A Tab while the next ghost text shows, any other key, a click, a focus change, a pause and a completion without a suggestion end the hold. While a completion runs, a typed key that continues the text that the completion added so far keeps its request, also when that text does not show yet. This does not occur when the earlier writing gives a phrase or next words for the new text. When the completion then gives no ghost text after the typed text, core asks again as after a typed key. Each session keeps the last 16 suggestions that the ghost text showed, each with its text before the caret (`ShownSuggestions`). When the text before the caret is such a text and then a start of its suggestion that is shorter than the suggestion, core shows the rest at once, with no request. Thus a backspace back to a place where a suggestion showed, or a retype of the suggested letters after a wrong letter, needs no model. Only the text of a completion goes into this memory, never a fix or a phrase. An earlier suggestion comes before a phrase. After a key, the ghost text shows only at a caret that moved from where the ghost text showed last (`GhostView::is_after_edit`), because a terminal moves its caret only after the program in it writes the text back. The ghost text and the badge show 40 ms after a key (`CARET_SETTLE_DELAY`), at the caret that the key moved. A suggestion that comes after this wait shows at once (`GhostTiming::Now`). While the ghost text does not show, core looks at the caret again every 20 ms, at most 20 times, and then shows the ghost text at the caret where it is. Only macOS does this check now. Each ghost text goes to the platform with its placement (`GhostView`). The ghost text after the caret has the color of the field text (`TextColor`) at the opacity `GHOST_TEXT_ALPHA` (half), as a placeholder. Light text (`TextColor::is_light`: more contrast with black than with white) gets the colors of a fix for a dark background. When the platform finds no caret, it can show the ghost text in the mirror next to the focused field. The mirror (also the card below the caret) shows the end of the typed word before the ghost text (`GhostView::typed_word`: the text after the last space, at most 24 characters, without the typo of a fix). The typed word has the primary text color and a semibold font. The ghost text has a lighter color with a contrast of at least 4.5:1. When text follows the caret on its line, the ghost text goes below the caret (`GhostPlacement::BelowCaret`), because at the caret it would cover that text. A suggestion also stops where it writes the text of that line again (`SHARED_UNITS`: from a word, or from the closing punctuation that starts that line, the words agree in at least 2 words and signs in a row, or up to the end of the shorter). A request inside a line has no cut of the tail and twice the tokens (`INSIDE_LINE_TOKEN_FACTOR`), because the end that fits the text after the caret ends the suggestion, and a sentence that the writer inserts can then finish. A field that hides the text of that line (`Surroundings::is_caret_line_hidden`: the input box of a terminal of xterm.js) always gets the ghost text below the caret, and no phrases. With the default preparation (at the first key), GhostType still prepares the prompt when the input settles in a place where the earlier writing has a text. A session lasts while the user types in the same field. After Enter, core reads the field again when the input settles or at the next key. When the field shows the text of the session (or the field text that core read at Enter, because a dead key or an autocorrect can change the typed text), line breaks, and then no letters, the session continues on the new line, and the settle asks the model for a suggestion there. Else the session ends. A dead key (`Key::Dead`) does not end the session. A click and a focus change still end the session. A screen read starts at the first key of a session and when the input settles, unless the session has its final screen text. A session first uses the stored screen text. The answer of its own read replaces that text one time, when the text changed. When the read of the accessibility tree gives no lines and the platform can do an OCR, core asks for an OCR read. The level of the Screen text pane (fast or accurate) shows only when the OCR of the platform has levels (`OcrLevels`). The `Controller` runs GhostType from the platform events (keys, clicks, timers, tray, settings window, service answers). Pure Rust, no OS. Each platform implements the `Shell` trait: it reads the desktop (`Desktop`) and does the OS effects that the controller asks for. The platform runtimes only translate OS events into controller calls. Core also holds the key-press rules (`Key::from_press`) and the badge click rule (`BadgeClickFilter`). Escape always counts, Tab only without a modifier, and Enter and Backspace only alone or with Shift. Any other key with a shortcut gives `Key::Other`. Else a key gives the typed character, a dead key, or `Key::Other` when it types no single character. Each platform maps its key codes and modifiers to the neutral kinds of `key`. Each pane (`settings_window`) gives its page of the settings window as a tree of sections and rows (`settings_window::view`), with a stable id for each control. Each row of a setting also has a picture before its label (`RowIcon`). Each platform has one renderer for each kind of row and sends back what the user did with a control, so a new setting needs no platform code.
- `ghosttype_windows`: hooks, overlay, badge at the caret, `SendInput`, tray (Win32, main thread). A fix shows a red line through the typed letters, as wide as the letters in the font of the overlay, and the fixed word in green (Fluent colors, or the colors of high contrast). Without the color of the field text (also in a terminal of xterm.js), the ghost text after the caret is a neutral gray (`NEUTRAL_GRAY`, the same in light and dark mode, so it shows on a light and on a dark background). In high contrast, it is `COLOR_GRAYTEXT`. When text follows the caret on its line, the overlay shows the typed word and the ghost text on a card below the line of the caret, with the ghost text under the caret, or above the line at the bottom of the work area. The card has the fill and the border of the Fluent tooltip, as the badge. The typed word and the typo of a fix are in the Fluent primary text color and semibold. The ghost text is in the Fluent secondary text color in light mode and the tertiary one in dark mode (`CardText`). In high contrast, they are `COLOR_WINDOWTEXT` and `COLOR_GRAYTEXT`. A replacement sends a Backspace key for each deleted character before the text. The shell queues each replacement, and each inject message types the oldest one. Caret reader on its own thread: the system caret, else the caret object of the focused window (`OBJID_CARET` of Microsoft Active Accessibility: Chromium browsers and Electron apps such as VS Code), else UI Automation (UIA) for apps that draw their own caret (WinUI). A caret shorter than a line of text does not count, because Qt apps such as Telegram keep a transparent 2 x 2 px system caret for input methods. In a terminal of xterm.js (the class `xterm-helper-textarea` in UIA), the caret moves up to the row of the terminal screen that holds the hidden input box, because VS Code draws that box below the top of its row. Each caret has the color of the text before it (UIA `ForegroundColor`), but not in a terminal of xterm.js, and not when that color is the `BackgroundColor`: Chromium drops the alpha of the transparent text of a hidden input box. It also reads the text around the caret (UIA `TextPattern`, else a classic edit control), the field labels (UIA `LabeledBy`, `Name`, then `HelpText`, else `FullDescription`) and the host of the web page (the URL in the value of the nearest Chromium or Gecko document) 40 ms after each key, click and focus move. The shell keeps that read for the hook, because the hook must not wait for UIA. A field that UIA marks as a password field (`IsPassword`) gets no suggestions. After a click or a focus move, the field also counts as a password field until the read of the new field answers. Screen text reader on its own thread with a low priority: the UIA text elements of the foreground window, else the OCR of a band of the window around the field (`Windows.Graphics.Capture` and `Windows.Media.Ocr`). The OCR needs Windows 11, because Windows 10 draws a border around the window at each capture. It stops while energy saver is on. Settings window (WinUI 3 through windows-reactor, on its own UI thread), as the Settings app: a color icon of the Fluent UI System Icons for each page in the navigation (`assets/fluent`, the page symbol in high contrast), and a glyph of the icon font at the leading edge of each card of a setting. The physical cores of the CPU and their efficiency classes (`cpu_cores`). All FFI.
- `ghosttype_macos`: event tap, Accessibility (AX) for the caret, the text around it, the field labels (`AXTitle`, else the text of `AXTitleUIElement`, `AXDescription`, `AXPlaceholderValue`, `AXHelp`) and the host of the web page, the static text of the focused window, else the OCR of a band of the window around the field (`ScreenCaptureKit` and Vision, only with the Screen & System Audio Recording permission). The screen reads run one at a time on a dispatch queue with a low priority. In a terminal of xterm.js (the class `xterm-helper-textarea` in `AXDOMClassList`), the caret is the left edge of that hidden input box, moved up to the row of the terminal screen that holds it. The text in the box does not give the caret, because xterm.js keeps the text that GhostType types there until Enter. Overlay panel (a fix: an attributed string with a red line through clear letters, then the fixed word in `systemGreen`). The overlay reads the color of the character before the caret (`AXForegroundColor` of `AXAttributedStringForRange`, not in a terminal of xterm.js, and not for text with an alpha below 0.5) and draws in `DarkAqua` behind light text, else in `Aqua`. With Increase Contrast, the ghost text is `secondaryLabelColor`. Without that color (also in a terminal of xterm.js), it is `systemGrayColor`, which is the same gray in the light and the dark appearance, so it shows on a light and on a dark background, the mirror for a field that gives no caret through AX (the editor of VS Code while its screen reader mode is off: an empty EditContext element). The mirror is a panel below the frame of the field, or above it, with the typed word in `labelColor` and the semibold system font, and the ghost text in `labelColor` at 60% opacity (`secondaryLabelColor` with Increase Contrast). A control without a text selection gets no mirror. When text follows the caret on its line, the mirror shows the typed word and the ghost text below the line of the caret, with the first letter of the ghost text under the caret, or above the line. CGEvent injection (a replacement posts a delete key for each deleted character first. The shell queues the replacements, and each inject pass types the oldest one), menu bar extra, settings window (a sidebar of the panes, each with its symbol on a colored tile, as in System Settings). All FFI. Needs Accessibility access (`cargo run` from a terminal: grant it to the terminal app). The OCR also needs Screen & System Audio Recording, which `cargo run` also takes from the terminal app.
- `ghosttype_models`: Hugging Face search, downloads and the local models directory (`ModelHub`). HTTPS + file IO, no FFI.
- `ghosttype_history`: the earlier writing in one encrypted file (`WritingHistory`), with `ring` for the cipher and the random key. It reads the key from the `KeyVault` of the platform (`ghosttype_macos::Keychain`, `ghosttype_windows::ProtectedKeyFile`) only at the first read or write. File IO, no FFI, no network.
- `ghosttype_settings`: the settings file (`SettingsFile`, the `SettingsStore` of core): the serde format of the settings and the migrations of old fields (`stored`). File IO, no FFI.
- `ghosttype_llm`: runs GGUF models with llama.cpp (`llama-cpp-2`) on one worker thread (`ModelRunner`), on the backend that each load names (CPU, Vulkan, CUDA, Metal). macOS always loads on Metal. On the CPU, a prompt runs one thread on each performance core of the `CpuCores` that the bin gives (at least 4 threads when the CPU has 4 cores), and each added token runs on at most 4 threads. Without `CpuCores` (macOS, tests, eval), and on the GPU backends, llama.cpp keeps its threads. Refuses a GPU load when the whole model does not fit in free GPU memory. When llama.cpp starts, it logs each device that llama.cpp found, because a release build of llama.cpp loads its GPU backends without a log. Heals the last word of each prompt (token healing), but never takes back a line break. Adds the next-word bias only to the first token that it adds. It finds the tokens that agree with the healed text in a sorted table of the token texts, which it makes at each load. Gives the log probability of each added word (at a healing step, the share of the token among the tokens that agree). Gives the log probability of the typed letters of the last word: the higher of the healing path and the tokens that cover the letters at the first healing step (`TypedLetters`), because the healing path can go through a lone space. It adds no text when the letters are less likely than the minimum of the request. When the request asks for fixes, it looks among the 64 most likely tokens at the start of the word for one that fixes the letters with one edit (a swap of two letters, a changed, an extra or a missing letter: `correction`). The fix keeps at least 3 letters and is not a typo itself. Then the completion starts again from the fixed letters with that token, and sends no parts. After the first word, it stops when the added text gets less likely than the cut of the request, and leaves out the word of that token. It stops before a new word after the end of a sentence: a period, "!", "?", "…" or the CJK signs 。！？, also before closing quotes and brackets. A period ends a sentence only after a word of at least 2 letters, because one letter is often an initial or the end of "e.g." or "a.m.". The word must also not be one of the English and Spanish `ABBREVIATIONS`, such as "Mrs.", "Sra." or "pág.". At the token limit, it leaves out the last word, unless that word ends a sentence or it is the only word. With text after the caret on its line (`line_after` of the request), each step also reads how likely the model finds the start of that line next (the tokens that agree with it, without the tokens of only whitespace, because Gemma writes a lone space before digits). The added text ends where the model finds the added text and then that line most likely, and the completion stops when the model starts to write that line. The parts show only up to that end. Before that line, a token that opens a placeholder (an opening square bracket before a letter or a digit) also stops the completion, because the ghost text ends before a placeholder. Keeps the last prompt in the llama.cpp cache, so the next prompt decodes only the tokens that it adds. For a recurrent model (Qwen3.5), it also saves the state before each of the last words, so a backspace across a word does not decode the full prompt again. Sends the text of a completion while it grows. A drop of `LlamaCpp` waits until the worker frees the model, because on Metal llama.cpp stops the process with an assert when the process exits with a loaded model (macOS quits through `exit`). With the "Show words early" setting, the engine shows its complete words at once. Build needs CMake and libclang.
- `ghosttype`: bin. Wiring, data folders, settings load, logging, event loop.

## Rules
`.claude/rules/` (binding; path-scoped ones load with matching files):
- `tdd.md` test-first workflow · `clean-code.md` naming, structure, no comments · `architecture.md` crate boundaries, traits
- `portability.md` logic in core; platform crates only translate, so OS ports never touch core
- `rust.md` API, errors, docs, types · `dependencies.md` Cargo · `windows.md` FFI, threads, runtime invariants · `windows-ui.md` Windows 11 look & feel (Fluent) · `macos-ui.md` macOS look & feel (Apple HIG, Liquid Glass) · `git.md` · `ste100.md` Simplified Technical English for prose and UI strings
